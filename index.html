AI Layer

TIP Intelligence

TIP Intelligence is not a chatbot. It is an active financial intelligence layer embedded into every workflow — surfacing the right context at the exact moment Paul needs to make a decision, detecting anomalies before they compound, and learning from every action Paul takes. This page explains what each component does, how it is architected, and what the dev team must build to power it.

AI is a first-class runtime component, not a bolt-on. The distinction matters architecturally: every screen sends a context snapshot on mount when AI is active. Every recommendation shown is logged. Every action taken (or not taken) feeds the feedback loop. The AI layer touches the data model, the API layer, and the frontend simultaneously. Do not design it as an optional feature that could be removed.

The Three AI Components

Ask TIP Rail

Amazon Bedrock · Claude Haiku 4.5

A persistent side rail accessible from every screen via Cmd+K (or the fixed FAB button, bottom-right). Screen-aware: knows which screen you're on, what data is visible, and what decisions are available. Answers questions, compares rates, surfaces deploy-vs-hold recommendations, and flags compliance issues — in plain language, in under 2 seconds.

Speed-optimised. Haiku 4.5 = fast conversational responses. Not used for heavy analysis.

Anomaly Detection Engine

Deterministic rules · Surfaced via Rail

11 rule-based checks that run against live portfolio and district data. Detects negative working capital, concentration limit breaches, stale source data, levy delta spikes, duplicate tax receipts, and inter-account transfers that affect TDF weighting. Signals are surfaced in the Ask TIP rail as contextual alerts — not separate notifications.

Deterministic, not ML. Rules are auditable and configurable via system_parameters.

PDF Statement Intelligence

Amazon Bedrock · Claude Sonnet 4.6

2 AI-parsed PDF institutions (FH Securities, Raymond James) deliver monthly statements in formats that vary by institution and cannot be structurally parsed. Sonnet 4.6 extracts position-level data — institution, CUSIP, balance, rate, maturity date, accrued interest — with per-field confidence scores. Positions queue for human review before being accepted. 9 additional institutions deliver structured CSV/XLSX files parsed deterministically. 3 institutions (AMAL Bank, Pan American Bank, Liberty Bank) are manual-entry-only — no parsing pipeline required.

Analytical-optimised. Sonnet 4.6 = high accuracy on complex unstructured documents. Async pipeline, not real-time.

Component 1 — Ask TIP Rail

Every session Paul opens TIP, the rail is available. It does not wait to be asked — it loads the current screen's context on mount. Paul can type a question or select from 4 suggested prompts that change based on which screen he is on.

How screen context works

When any screen mounts, the frontend calls POST /screens/:id/snap to save a context snapshot. That snapshot — what positions are visible, what the current close period is, what alerts are active — is passed with every Ask TIP query as screen_context in the request body. Without this, the AI is answering generic questions. With it, the AI is answering questions about Paul's specific portfolio, right now.

Component 2 — Anomaly Detection Engine

This component runs on the server, not in Bedrock. It is deterministic rule evaluation over portfolio and district data. The results are surfaced as signals in the Ask TIP rail — not as separate notification systems.

Anomaly rules — 13 total, 5 severity levels (3 TDF · 3 Tax Allocation · 2 Compliance · 3 Cash Flow · 2 Portfolio)

Each domain has its own server-side evaluator. The Cash Flow evaluator (computeForecastAnomalies) defines 4 rule slots — Rule 4 is deprecated and removed; 3 active rules remain: (1) floor breach, (2) buffer compression, (3) surplus deployment opportunity. Component 3 — PDF Statement Intelligence

2 AI-parsed PDF institutions (FH Securities, Raymond James) provide monthly statements in unstructured formats. Claude Sonnet 4.6 reads each PDF and returns structured JSON. A human reviews the extracted positions before they are accepted. 9 other custodian institutions deliver structured CSV/XLSX files parsed deterministically. 3 institutions (AMAL Bank, Pan American Bank, Liberty Bank) are manual-entry-only — no parsing pipeline required.

Pipeline flow

1. UploadOps (Hope) downloads PDF from custodian portal, uploads via TIP UI → S3 presigned URL → POST /statements/:id/upload
2. QueueUpload trigger writes a job to SQS with { statement_id, s3_key, institution_id, tenant_id }
3. Lambda workerPicks up SQS message, reads PDF bytes from S3, calls Amazon Bedrock with Claude Sonnet 4.6
4. Bedrock extractionSonnet 4.6 returns structured JSON per the response schema below. Lambda writes rows to parsed_positions.
5. Review gatePositions with confidence_score < 0.80 are flagged. Ops reviews flagged rows before accepting.
6. AcceptOps accepts or overrides each row → positions written to positions table. Statement marked status='processed'. (Note: prototype uses "portfolio_positions" here — canonical table name is positions.)

Every recommendation TIP surfaces is logged. Every action Paul takes — or doesn't take — feeds back into that log. This is the closed loop that makes TIP more useful over time. V1 collects the data. V2 uses it to personalise recommendations per tenant.

What TIP Intelligence Is Not

Not thisWhy it matters for implementation
Not a general-purpose chatbotThe system prompt scopes every Ask TIP response to treasury operations for the current tenant. Off-topic questions return a redirect, not an answer. The dev team does not expose a general Bedrock endpoint.
Not autonomousTIP Intelligence never executes a trade, posts a JE, or changes data without Paul confirming. Every AI recommendation is a suggestion — the action button is always a human click. The API enforces this: AI endpoints are read-only for portfolio data.
Not real-time market dataTIP works with ingested data — bank CSV via SFTP, Tyler Tech CSV via SFTP, custodian PDFs. There is no live market data feed in V1. The ILF benchmark rate is updated manually in system_parameters. The AI answers questions about Paul's portfolio as it exists in the database, not as the market moves.
Not always-on for all tenantsAll three AI components are behind feature flags: ai_recommendations, ask_holicow, ai_statement_parsing. A tenant can be provisioned with all three off. The platform admin Feature Flags screen controls them per tenant. Build the feature flag checks into every AI code path.
Not replacing Paul's judgmentTIP Intelligence surfaces context and asks the right question at the right moment. It does not make the decision. The fiduciary responsibility under 30 ILCS 235 remains with the Treasurer. The Decision Log records Paul's rationale — not TIP's.

Treasurer Attestation — 30 ILCS 235/2.5

The Board Report screen requires a Treasurer digital signature before the report can be filed. The API must:

  2. Verify all 9 close steps are complete for the period (return 409 otherwise)

Statutory language pre-populated in the frontend attestation step — the API does not validate the language, only the authorization and preconditions.
